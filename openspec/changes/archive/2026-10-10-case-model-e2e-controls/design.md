# Design

## Intent and boundaries
Build evidence that the existing case inputs traverse the actual platform, PostgreSQL job service and selected provider, and make state/work execution observable. Do not equate green JSON tests, scripted model responses, one source family, or author labels with calibrated semantic accuracy.

## Replay representation
Use catalog-validated sources `case-002`, `case-002-n4`, `minimal`: sixteen cutoffs, one logistics family plus a UI control. Each cutoff becomes a separate platform case because frozen v1 participants cannot grow, and declaring later actors at an earlier cutoff leaks future information. The replay ID records run/source/cutoff. Declare only actors visible at that cutoff. Map source messages one-to-one into canonical events; preserve IDs, direction and original English body where present. Normalize source timestamps to aware ISO format. Use an explicit internal source-context event for the original goal and visible actors' names/roles. This is untrusted case-card evidence, not system instructions or authority. Record the transformation and source-to-platform event mapping. Never include source `agent_state`, next steps, facts/decisions/annotations or later messages in that event. Initial source context alone cannot authorize a business action.

References remain in a separate expectations ledger. Manually specify acceptable state/action/wait-target sets and whether completion is supported at each cutoff; label author-derived expectations unvalidated. Initial cutoffs are insufficient-evidence controls, not automatic exact-state gold. Test known-good and mutated-bad candidates so the checker can detect premature completion, wrong waiting target and invented evidence. All source branches stay in the development split; no held-out accuracy claim.

## Interfaces
`tools.dwelly_e2e.cases.build_case(source_id, step_index, run_id)` returns a JSON object with `case_id`, `source`, `declaration`, `events`, `expectation`; `case_plans(run_id)` returns all sixteen in stable order. Case IDs are valid v1 identifiers. `source` includes source hash/family/cutoff and input transformation qualification. `expectation` never enters uploaded events.

`tools.dwelly_e2e.checks.evaluate(job, detail, plan)` returns named checks, each with `status` pass/fail/not_run, `category` semantic/operational, actual and expected. Missing or failed output cannot become a semantic pass. Check source binding, visible evidence, state/wait/action expectations, no unsupported completion, and no operational effects. `summarize(records, mode)` keeps operational and semantic totals separate and marks simulated semantics as fixture-only.

`python -m tools.dwelly_e2e run --base-url URL --mode live|simulated --profile ID --output NEW_DIR --run-id ID [--limit N]` uses actual HTTP routes. Preflight requires enabled/available selected profile, exact local origin and correct mode; simulated IDs cannot count as live. Snapshot upload, frozen submission, bounded polling, same-key replay and durable GET readback use deterministic per-run keys. Save input, expectation, job/receipt, check results and a report. No automatic provider retry, overwrite, remote origin or secret copying. Polling has a deadline and yields not_run/unavailable rather than success if infrastructure cannot finish. Each plan has one job per profile; cap source cuts at 16 and profiles per command at 1. Run separate provider commands under one shared experiment scope.

After a completed checkpoint, append a clearly labeled synthetic later event to a dedicated final probe case or the last checkpoint, verify old analysis becomes stale, reject a new submission against its old revision, and replay the original key without a second dispatch. This operational mutation must not enter the semantic score for the earlier frozen snapshot.

## Browser and work control
Keep model transport lifecycle separate from coordination inference and case lifecycle. UI renders candidate coordination state, waiting actor IDs, next proposed action, current/stale binding, dispatch attempts and zero-effect status. Poll only GET for nonterminal jobs in the selected case; stop on terminal status or selection change. Reload resumes observation, not submission. A model `completed` never sets case `resolved` or authorizes execution.

The browser fixture owns an isolated database schema and a clearly named scripted provider. It uses real platform HTTP, PostgreSQL and worker code; only the external transport is substituted. It replays authored cases, triggers a model from the UI, observes terminal state, reloads and checks stale state. It also tests failed/unknown jobs and no resubmission on GET/reload. Its reports explicitly say zero live calls. Live API runner receipts and an actual live UI canary are separate when keys are available.

## Verification and stop rules
TDD for replay/checker, runner and UI polling. Independent review tests leakage, mode labeling, actual response/model identity, secret handling, idempotency and stale-action boundaries. Run selected canonical regression plus Node and browser paths. At most one provider attempt per checkpoint/profile. Stop an affected provider on authentication, budget or unknown-dispatch errors; keep raw failure evidence. Preserve user drafts. No public push or cloud deploy in this slice. Live readiness is unavailable until keys are supplied; implementation and scripted verification can proceed meanwhile.
