## Why

The completed cross-provider review found useful design gaps in partial outcomes, routing authority, recovery and assessment isolation. The v2.2 manuscript and fresh review provide the preparation baseline, not an executable competition entry. On 7 October the user agreed to begin an offline MVP and requested more connections and an updated plan. This change now describes the implementation candidate, while preserving the two logistics workflow families and keeping document review separate from runtime evidence.

The user confirmed six integration adapters and answered 18 design questions. This revision is dated 8 October 2026, Europe/London. Product priorities are now explicit: easy integration into existing systems, rapid adaptation to an unfamiliar environment, then reliable case resolution. The primary user is the engineer connecting the platform. This is a reusable harness and competition entry, not another vertical chatbot. The updated written design and tasks remain review candidates; answers approve the stated choices, not an unseen design or completed implementation.

## What Changes

- Define independent goods refusal, return creation, service refusal and operator delivery postconditions.
- Specify typed routing from authoritative object records before every external effect.
- Select a single-process SQLite intent journal and bounded restart reconciliation as the baseline.
- Specify acknowledgement/readback AND process adaptation, finite provisional caps and discovery exit conditions.
- Define enforced oracle isolation, human holdout custody when feasible and failure applicability across operations; development by the user and agents does not require inventing five available human developers.
- Add six narrow offline adapter surfaces: case records, delivery operations, scheduling, returns, customer messaging and operator inbox.
- Add explicit logical request generations, cross-adapter authority/version binding, capability profiles and operation-specific acknowledgement/readback contracts.
- Retain flat/nested no-text profiles while adding required free-text, transcript, image, PDF and raw-audio intake with explicit processing/provenance status.
- Select a Python modular monolith, Pydantic, SQLite, CLI/library/local API, provider-neutral extraction/planning interfaces, an Anthropic text/vision/PDF route and ElevenLabs transcription route as the proposed engineering bet.
- Add versioned process contracts and AI-proposed adapter/process changes that require regression and human approval before release; runtime cannot rewrite itself.
- Permit constrained autonomous slot selection, whole-order goods refusal/return, both clarification modes and evidence-rich operator decisions without autonomous financial execution.
- Define four separate 600-second acceptance targets: new-profile adaptation, positive-case completion, crash recovery and unsafe-action rejection. Define LLM labels as provisional pending team revalidation.
- Ground offline provider shapes in public Dwelly and logistics documentation without claiming a native Dwelly API or live vendor integration.
- Add system-generated official case output, bounded batch preparation and independent reproduction gates.
- Update this active OpenSpec design and task list with ownership roles, effort estimates and exit evidence, without rewriting the frozen v2.2 package or judge packet.
- These are proposed requirements. No target runtime implementation, live integration, runtime test or new provider assessment is included in this planning revision.

- `adaptive-assessment-preparation`: Discovery, adaptation measurement, oracle isolation and holdout custody.
- `offline-integration-bundle`: Six scoped adapter surfaces, evidence-bound capability manifests and structured input adaptation.

### Modified Capabilities

None. The existing living `proposal-document-control` capability is not changed by this runtime proposal.

## Impact

Current delivery is an updated implementation candidate, not product code. After written-design approval, the detailed Superpowers implementation plan belongs in `docs/superpowers/plans/`. Implementation is proposed inside a clean `runtime/` subtree with the `proofkey` package, tests, public fixtures and Apache-2.0 licensing for owned new code. This separates releasable source from private evidence; it is not a new nested Git repository. No source subtree, dependency installation or runtime invocation is created by this revision.

Future work affects ScopeRouter, PolicyGate, CaseStore, ActionGateway, Verifier, OperatorQueue, adapters, exporter and evaluation infrastructure. The archived reference code, v2.2 documents/ZIP, raw evidence and prior five-provider outputs remain unchanged. The change must not be archived as an implemented runtime until written design review, implementation, verification and acceptance are complete. Public release, event eligibility, live accounts and spending remain separate gates.
