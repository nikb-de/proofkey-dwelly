# Разметка кейса для виджета `case-step-viewer/1.0`

Виджет (`index.html` + `viewer.js`) проигрывает кейс по шагам: сверху шаги, слева JSON состояния с подсветкой изменений, справа чат, отдельно карточка заявки с критериями завершения и состояние агента. Один JSON на кейс.

Мы играем за **деск координации** (Iona Quill, Rivet Delivery Desk): получаем эскалацию, понимаем, чего не хватает для решения, у кого это запросить, ждём ответ, фиксируем подтверждение.

## Разделение труда

Скрипт `pipeline/compile.py` берёт из источника сам: сообщения (текст EN, перевод RU из атласа, канал, время, от кого → кому), вложения, даты создания и эскалации, тип события (`message_sent` если пишем мы, иначе `message_received`), появление участников в состоянии по мере первого упоминания.

Разметчик пишет **смысл**: кто есть кто, цель, препятствие, факты с источниками, запросы, критерии завершения, состояние агента на каждом шаге, обоснование шага, пояснения о пробелах истории.

## Файлы и команды

- `briefs/<branch>.md` — карточка и полная история негативной ветки. Публичные первоисточники: `data/dwelly-public-cases/raw/Delivery & Logistics/0NN/`; негативные: `data/negative-branches-001-050/`. Конвейер работает внутри этого репозитория; `PROOFKEY_REPO`, `PROOFKEY_PUBLIC` и `PROOFKEY_ATLAS` — необязательные переопределения источников.
- `annot/002.json` — эталон разметки. `cases/002.json` — во что он компилируется. Прочитать оба перед работой.
- `annot/0NN.json` — то, что пишет разметчик.
- Сборка и проверка (из папки `case-state-widget`):

```bash
python3 pipeline/compile.py 0NN && node pipeline/validate.mjs cases/0NN.json
```

Чинить до `OK`. Предупреждения `⚠` прочитать и либо исправить, либо объяснить в отчёте.

Правки кейсов вносить в `annot/<id>.json`, затем собирать `cases/<id>.json`. `annotate_negative.py` создаёт недостающие ветки по авторским историям; обычный запуск сохраняет существующую разметку. `--refresh` явно пересоздаёт 274 автоматически размеченные ветки и перезаписывает их ручные правки. Эталон 002-N4 сохраняется всегда.

`source_attachments` задаёт оригинальный дескриптор вложения и событие его первого появления: `[{"event_id": "004", "attachment": {"name": "...", "type": "...", "url": "..."}}]`. Это сохраняет публичные вложения без зависимости от внешнего атласа, в том числе в унаследованных шагах негативных веток.

`criteria_retire` на шаге расхождения содержит id исходных критериев вне задачи этой ветки. Компилятор переносит их в `prior_success_criteria` со статусом на момент смены рамки и `retired_at_event`, не объявляя их выполненными. Новый `branch_resolution` проверяет конкретную задачу координации, а итог дословно сохраняет подтверждение и ограничения последнего события. Для 002-N4 сохраняются исходные критерии: подтверждение адресного деска действительно закрывает их.

Проверка всех 325 кейсов из корня репозитория:

```bash
python3 case-state-widget/pipeline/compile.py --all
python3 case-state-widget/pipeline/test_negative.py
node case-state-widget/pipeline/validate.mjs case-state-widget/cases/*.json
npm test --prefix case-state-widget
```

Датасетные тесты проверяют воспроизводимость всех сборок, полное совпадение унаследованных состояний, SHA-256 первоисточников, дословность сообщений, отсутствие раннего завершения, 34 проверки неизвестного исхода и отказ от ответа за молчащую сторону после дедлайна. Движковый валидатор учитывает время уже наступившего события как известные сведения.

### Поля

**actors.** Ключ — короткий смысловой id латиницей (`coordinator`, `recipient`, `sender`, `dispatch`, `depot`, `carrier_desk`, `address_desk`, `broker`, `pickup_point`, `warehouse`). `source_names` — строки `From:`/`To:` из истории **дословно** (участник может встречаться под несколькими строками — перечислить все). Каждая строка From/To кейса обязана попасть ровно к одному участнику. Если `To` содержит несколько адресатов через `;`, каждого сопоставить отдельно. `from_start: true` — только для нас и для клиента (они известны из карточки). Остальные появятся в состоянии при первом сообщении или первом запросе к ним. `responsibility` — за что этот участник отвечает именно в этом кейсе. `client_actor_id` — тот, чьё обращение мы ведём (Source role в карточке); `null`, если клиента в этом смысле нет.

**role участника.** Короткое английское слово по функции в кейсе: `coordinator` (мы), `recipient`, `sender`, `customer`, `merchant` (продавец и его службы: refunds, returns — или точнее `returns_desk`), `dispatch`, `scheduling`, `depot`, `warehouse`, `carrier` (службы перевозчика без более точного слова: tracking support, routing, recipient services, notification support), `address_desk`, `broker`, `pickup_point`, `safety_desk`, `account_team`, `billing`, `driver`, `system` (автоответчики и формы). Список открытый: если функция другая, взять короткое английское слово по той же логике и упомянуть в отчёте. `executor` не использовать. Роль видна в интерфейсе рядом с именем.

**limits.** Верхний уровень разметки (формулировать без чисел и названий из поздних событий: не «GBP 18.00 due», а «do not state the amount before billing confirms it»): массив коротких запретов по-английски из раздела карточки «Boundaries and remaining work» (строка «Must not: …», «No delivery claim» и т.п.). Компилятор ставит один и тот же список в `initial_state` и в каждый `state_after`; пустой список не пишется. Это поле добавил Алишер (PR #3, 10.10.2026) вместо динамического `constraints` из первой версии 002-N4; `constraints` больше не используется.

**goal / blocker.** Цель — в терминах координации (получить сведения, согласовать, добиться подтверждения), а не «доставить посылку», если карточка явно ограничивает задачу (`Status: Completed — specific coordination task only`). `blocker` меняется по шагам; `null`, когда препятствий нет.

**facts.** Массив `{id, text, source}`. `source.type` — `case_card` (id = номер кейса) или `message` (id = номер события). Факт — одно утверждение. Уточнение факта: тот же `id`, новые `text` и `source` (эталон: f2 «адрес неполон» → «блокировка снята»). Начальные факты — только из карточки (разделы Case details, Context). Никаких полей вида `building_confirmed: true` — только текст. Факты из сообщения появляются на шаге этого сообщения, не раньше.

**requests.** Словарь `rid → {type, from_actor, to_actor, responsible_actor, purpose, expected_response, status, response, evidence_event_ids}`.
- `type`: `information` (нужен факт) · `decision` (нужно выбрать между вариантами) · `permission` (нужно разрешение/согласие) · `action` (нужно что-то сделать) · `confirmation` (нужно подтвердить выполнение) · `verification` (нужно проверить исход уже сделанного, прежде чем действовать дальше).
- `status` для наших запросов: `planned` → `awaiting_response` → `answered` | `completed` (для action) | `declined`. Для входящих просьб к нам: `received` → `answered`. В негативных ветках также `outcome_unknown` (действие сделано, результат неизвестен) и `superseded` (запрос потерял смысл, его заменил другой).
- `responsible_actor` — кто обязан дать ответ или выполнить. `responded_by` — кто фактически ответил, если это не `to_actor` (в том числе для r0 клиента, когда по существу ответил исполнитель) (например, писали диспетчеру, а ответил склад); ключ появляется только на шаге ответа вместе со статусом `answered`/`completed`/`declined`. `evidence_event_ids` — события, где запрос появился и где закрыт; `answered`/`completed` без подтверждающего события не бывает.
- `requests_upsert` на шаге — полная замена объекта запроса по ключу.

**decision.** `{required, question, options: [{id, label, conditions}], decision_maker, selected_option, reason}`. Заполнять, когда в кейсе есть выбор (перенос на другой слот, возврат или повторная доставка, забрать самому или ждать). Если выбора нет — не указывать, компилятор подставит `required: false`.

**success_criteria.** Объявляются в `initial` (обычно 2–3), формулируются как проверяемые подтверждения в рамках задачи карточки (раздел Outcome). В шагах `criteria_met: [{"id": "c1", "evidence_event_ids": ["004"]}]` — когда сообщение их подтверждает. Доставка не входит в критерии, если карточка пишет `No delivery claim`.

**agent_state.** `status`: `ready` (можем действовать) · `acting` · `waiting` (ждём ответа) · `completed`. `waiting_for: [{actor_id, request_id, expected}]` — обязательно при `waiting`, пусто иначе. `next_action` — что делаем дальше, `null` при `completed`. `note` — пояснение, если состояние неочевидно (например, промежуточный шаг не записан в истории).
- После нашего исходящего запроса → `waiting` на того, кому написали.
- После ответа, который требует нашего следующего действия → `ready` с `next_action`.
- После подтверждения, закрывающего критерии → `completed` на последнем шаге, если карточка говорит Completed.

**status кейса.** `not_started` (старт) · `context_received` (после события Context) · `escalated` (после эскалации, пока мы не ответили) · `awaiting_response` (ждём сведений или разрешения: запрос типа information/permission) · `awaiting_decision` (ждём выбора: запрос типа decision) · `awaiting_confirmation` (ждём подтверждения исполнителя по action/confirmation; ставится и когда наш запрос исполнителю подразумевается, но не записан в истории) · `awaiting_verification` (ждём от исполнителя проверки исхода) · `action_required` · `verification_required` · `in_progress` · `blocked` · `completed`.

**next_step.** `{type, responsible_actor, request_id | null, description}` или `null`. `null` допустим и на шаге Context, когда ещё не известно, кто действует дальше (клиент ещё не написал). Если следующий ход наш и запроса к кому-то пока нет (например, уведомить клиента), пишется `{type: "action", responsible_actor: "coordinator", request_id: null, description}` и статус `action_required`; при `responsible_actor: coordinator` тип всегда `action`. Раздел карточки «Initial request» — это текст события 002: на шаге 001 он ещё не известен деску.

**Что известно на момент эскалации.** Раздел карточки «Next action at escalation» — знание деска на шаге эскалации (002): исполнителя, названного там, можно ввести запланированным запросом уже на 002, до его первого сообщения. Разделы «Outcome» и «Boundaries» — не знание, а рамка: из них берутся формулировки критериев и `limits`, но без названий, кодов и чисел, которые появляются только в поздних событиях.

**Закрытие входящей просьбы клиента (r0).** `answered`, когда клиент получил ответ по существу; `completed`, когда просьба была о действии и исполнитель подтвердил его (даже если наш ответ клиенту не записан). Если Outcome карточки — «клиент уведомлён / получил инструкции», критерий считается `met` по нашему исходящему сообщению: это единственное возможное подтверждение. Просьба третьей стороны к клиенту при нас в копии (например, scheduling → recipient) ведётся как обычный запрос со статусами `planned/awaiting_response → answered`.

**result.** На последнем шаге при завершении: `{summary, confirmed_by, evidence_event_ids, remaining_work}`. `remaining_work` — что осталось вне задачи деска (перевозка, вручение).

**Негативные ветки** (`case_id` вида `002-N4`, источник `data/negative-branches-001-050/`). События 001–00N унаследованы от публичного кейса, разметка этих шагов совпадает с позитивной. На шаге расхождения: `criteria_add` — новые критерии, которые появились из-за сбоя; `intake_update` — изменившаяся сводка заявки (`summary`, `note`); запреты ветки идут в верхнеуровневый `limits` (а не в `constraints`); `decision` с вариантами `{id, action, allowed, reason}`. Факты, унаследованные из карточки родительского кейса, ссылаются на `case_card` с id родителя (`002`). Верхнеуровневый `provenance` описывает источник ветки (см. `annot/002-N4.json`).

**annotations_add.** Пояснения `{id, kind, title, text, before_message_id?, source_event_ids, implied_action?}`. **Пропущенные шаги истории** — отдельная обязательная проверка: для каждого события спросить, какое наше действие должно было произойти до него, чтобы оно стало возможным (запросить варианты у диспетчера, передать выбор клиента исполнителю, запросить подтверждение). Если такого действия нет в записях, добавить пояснение `kind: gap` с `before_message_id` того события, которое его подразумевает, и `implied_action: {from_actor, to_actor, type, purpose}`; косвенное подтверждение (например, «Following your booking request…») указать в тексте. Пример: `annot/001.json`, шаги 004 (пробел как «следующее действие», без `before_message_id`) и 005 (тот же `id`, теперь с `before_message_id: "005"` и цитатой косвенного подтверждения); шаг 003 там — пример `kind: context` для обратного случая, когда действие не требовалось (слоты уже пришли в 001). `implied_action.from_actor` может быть и третьей стороной, если пропущен чужой шаг (маршрутизация → пункт выдачи, служба → склад). Если событие могло быть и инициативой другой стороны, пробел остаётся, а неопределённость называется в тексте. Валидатор требует `implied_action` у каждого `gap`. `kind`: `context` — что участник знал до своего сообщения (показывается в чате перед сообщением `before_message_id`); `gap` — пробел истории: действие или ожидание, которого нет в записях, но которое подразумевается. Повтор `id` на следующем шаге заменяет текст.

**Несколько адресатов.** Если в `To:` события перечислены двое через `;`, компилятор ставит первого в `to_actor`, остальных в `messages[].copy_to` (поле Алишера). Разметчик ничего не делает, кроме сопоставления обоих в `source_names`.

**conversation_id.** Группировка переписок: `client` (мы ↔ клиент), `service`/`dispatch`/`depot` и т.п. (мы ↔ исполнитель). Если сообщение адресовано двум сторонам — та переписка, к которой относится основной адресат (первый в `To`).

**label / title / explanation.** `label` — 1–2 слова для кнопки шага («Письмо службы», «Наш вопрос», «Ответ клиента»). `title` — что произошло. `explanation` — рассуждение деска: что это меняет и почему следующий ход такой.

## Правила точности

1. **Только источник.** Каждое утверждение в facts, requests, criteria, result должно опираться на карточку или событие с указанным id. Ничего «логично вытекающего».
2. **Никакого будущего.** На шаге N нельзя использовать то, что известно только из событий > N. Валидатор ловит коды и числа; смысловые утечки — на совести разметчика.
3. **Не приписывать действия.** Если история не записала наше исходящее сообщение, а позже приходит подтверждение, — агент на промежуточном шаге `ready` с `next_action` и `note`, плюс `annotations_add` с `kind: gap`. Не выдумывать `waiting` на неотправленный запрос (эталон, шаг 004).
4. **Различать:** запрос ≠ согласование ≠ бронирование ≠ фактическое выполнение. Критерий `met` только по подтверждению исполнителя или клиента.
5. **Границы карточки.** Раздел «Boundaries and remaining work» определяет, что не считается выполненным, и попадает в `result.remaining_work` или `note`.
6. **Вложения** попадают в JSON автоматически на шаге события, в тексте которого упомянуто имя файла; в фактах ссылаться на них как на содержание этого события.
7. **Язык.** Все тексты по-английски (`"lang": "en"` в разметке; `body_ru` не пишется), кроме случаев, когда явно просят русскую сборку. Пишите полными фразами, без пустых связок. Имена, коды отправлений, адреса, термины (hold, slot, dispatch, address desk) — как в источнике.
