# Виджет разбора обращения по шагам

Описание для аналитиков, разработчиков и авторов новых кейсов.

Рабочий пример: [кейс 002](https://dwelly-logistics-atlas.fly.dev/state-002.html). Полные данные: [case-002.json](case-002.json). Формальная структура: [schema.json](schema.json). Краткая инструкция по подключению: [README.md](README.md).

## 1. Что показывает виджет

Виджет воспроизводит обработку обращения с позиции агента-координатора. На каждом шаге видно, что произошло, кто кому написал, что теперь известно, какое действие доступно агенту, кого он ждёт и выполнены ли условия завершения.

Координатор — это **мы**. Он ведёт коммуникацию и добивается результата. Внешний исполнитель выполняет свою часть работы: например, адресная служба изменяет адрес в заказе. Клиент сообщает сведения, формулирует просьбу или даёт разрешение.

Вход виджета — один JSON: исходное состояние и последовательность событий с полными состояниями после них. Этот файл содержит и переписку, и данные обращения. Движок отображает переданные сведения и вычисляет различия между соседними состояниями. Решения и пояснения заранее записывает автор кейса или внешняя система.

Такой формат можно применять к разным обращениям: уточнению данных, согласованию решения, запросу разрешения, передаче задачи исполнителю и получению подтверждения результата.

## 2. Как читать экран

Сверху расположены кнопки шагов, «Назад» и «Следующий шаг». «Старт» показывает исходные данные до первого события. При переходе можно вернуться к любому уже описанному состоянию.

Под переключателем показаны текущее событие, краткое обоснование и состояние агента. Наше исходящее сообщение выделено явно. Когда агент ждёт, экран указывает конкретного участника и ожидаемый ответ.

Отдельный блок заявки содержит суть обращения и сведения о его создании, если они известны. Ниже критерии завершения расположены строками: условие слева, статус и подтверждающие события справа. Счётчик показывает число выполненных критериев.

Основная рабочая область состоит из двух частей:

- **JSON состояния слева.** Полная структура с ключами, значениями и вложенностью. Жёлтым выделяются изменения относительно предыдущего шага. Удалённые поля перечислены в раскрываемом блоке JSON Patch под рабочей областью.
- **Переписка справа.** Единая лента сообщений всех участников. В каждом сообщении указаны отправитель, адресат, канал и время, если они есть в данных. Наши сообщения выровнены вправо, входящие — влево. Сообщение текущего шага выделено рамкой.

Пояснения к источнику показаны отдельно от сообщений. Например, «клиент сообщил, что увидел статус на странице отслеживания» не превращается в выдуманное письмо клиенту.

На узком экране переписка и JSON располагаются друг под другом. Загрузка JSON, вставка текста и скачивание файла доступны в верхней части страницы.

## 3. Основные понятия

| Понятие | Смысл | Где хранится |
|---|---|---|
| Заявка | Зачем начато обращение, что нужно получить в результате | `goal`, `intake` |
| Участник | Человек или служба с ролью и ответственностью | `actors` |
| Событие | То, что произошло на конкретном шаге | `steps[].event` |
| Сообщение | Конкретный текст от одного участника другому | `messages[]` |
| Факт | Сведения, известные на этом шаге, со ссылкой на источник | `facts[]` |
| Запрос | Кто от кого ждёт информацию, разрешение, действие или подтверждение | `requests` |
| Решение | Вопрос выбора, варианты, ответственный за выбор и выбранный вариант | `decision` |
| Состояние агента | Может действовать, действует, ждёт или завершил работу | `agent_state` |
| Критерий завершения | Проверяемое условие, по которому оцениваем результат | `success_criteria[]` |
| Результат | Что достигнуто и кем подтверждено | `result` |

Событие и сообщение связаны, но имеют разные задачи. Событие задаёт шаг воспроизведения; сообщение содержит текст коммуникации. Создание заявки может быть отдельным событием, только если оно действительно присутствует в источнике. Дата создания из карточки обращения сама по себе не доказывает наличие отдельной системной записи.

Запрос тоже не равен сообщению. Одно сообщение может содержать несколько просьб, а один запрос — проходить через несколько сообщений. Например, просьба клиента исправить адрес адресована нам, но отвечает за внесение изменения адресная служба.

## 4. Формат входного JSON

Обязательные поля верхнего уровня:

| Поле | Содержание |
|---|---|
| `schema_version` | Строго `case-step-viewer/1.0` |
| `title` | Название кейса |
| `initial_state` | Полное исходное состояние |
| `steps` | Упорядоченный массив шагов; максимум 1000 |

Необязательное поле `initial_explanation` содержит пояснение к исходному состоянию.

Каждый шаг содержит три обязательных поля:

| Поле | Содержание |
|---|---|
| `event` | Идентификатор, тип и описание события |
| `explanation` | Краткое обоснование состояния или следующего действия |
| `state_after` | Полный JSON состояния после события |

`state_after` — полный снимок, включая неизменившиеся поля. Автору не нужно вручную составлять патчи. При выборе шага движок берёт соответствующий снимок и сравнивает его с предыдущим; на первом шаге — с `initial_state`.

Порядок определяется массивом `steps`, а не сортировкой времени. Идентификаторы событий должны быть уникальными. Временные отметки выводятся как переданные строки; движок не переводит их между часовыми поясами. В кейсе 002 используется UTC.

### События

| `event.type` | Значение |
|---|---|
| `message_received` | Входящее сообщение с позиции нашего агента |
| `message_sent` | Отправленное нашим агентом сообщение |
| `action` | Совершённое действие, которое может не быть сообщением |
| `state_changed` | Зафиксированное изменение состояния |

В `event` обязательны `id`, `type`, `title`. Дополнительно можно передать `label` для короткого названия кнопки, `timestamp`, `actor_id` и `message_id`.

Для обычного шага с новым сообщением используйте одно значение в `event.id`, `event.message_id` и `messages[].event_id`. Это согласует шаг, текст и ссылки на источник. `message_id` указывает, какое сообщение выделить в ленте.

`explanation` — короткое проверяемое пояснение: какие сведения позволяют действовать и почему выбрано такое действие. Например: «Номер квартиры получен, но служба ещё не подтвердила исправление». Это авторское объяснение сценария, а не журнал внутреннего рассуждения модели.

## 5. Состояние: обязательная основа и свободные данные

Движок использует обязательную основу: `actors`, `our_actor_id`, `goal`, `agent_state`, `success_criteria`, `messages`. У неё одинаковый смысл во всех кейсах.

Остальные предметные сведения можно описывать свободнее. В кейсе 002 используются `facts`, `requests`, `decision`, `result`, `blocker` и другие поля. Они отображаются в JSON и участвуют в подсветке изменений, но движок не интерпретирует их бизнес-логику.

Это позволяет описывать подтверждение здания как факт с источником, вместо добавления специального поля вроде `building_confirmed_by_recipient`. Структура остаётся пригодной для других предметных областей.

### Участники и заявка

`actors` — объект со стабильными идентификаторами участников. Ссылки в сообщениях, ожиданиях и запросах используют эти идентификаторы.

```json
{
  "our_actor_id": "coordinator",
  "client_actor_id": "recipient",
  "actors": {
    "coordinator": {
      "name": "Iona Quill",
      "organization": "Rivet Delivery Desk",
      "role": "coordinator",
      "responsibility": "Получить сведения и подтверждение выполнения."
    },
    "recipient": {
      "name": "Tarin Mave",
      "role": "recipient",
      "responsibility": "Сообщить недостающий номер квартиры."
    }
  }
}
```

Это фрагмент состояния. `our_actor_id` определяет, кто «мы», включая направление пузырей в чате. `client_actor_id` необязателен. Для подписи сообщения движок использует имя и роль; организация и ответственность доступны в JSON.

Участники, известные из исходной карточки, должны присутствовать сразу. Если участник становится известен только из следующего события, он появляется в соответствующем снимке. В текущем 002 координатор и получатель заданы на старте, адресная служба добавляется на 001.

`goal` описывает ожидаемый итог обращения. `intake`, если заполнен, может содержать `summary`, `created_at`, `escalated_at`, `note`. Отсутствующие сведения допустимо оставить неизвестными; не следует придумывать время или отдельное событие создания заявки.

### Факты

Рекомендуемая структура факта — идентификатор, текст и источник:

```json
{
  "id": "f6",
  "text": "Получатель сообщил квартиру 4B; улица и здание остаются прежними.",
  "source": { "type": "message", "id": "004" }
}
```

Факты описывают знания на выбранном шаге. После нового подтверждения текущий факт может обновиться; предыдущая версия останется в более раннем снимке. Переписка при этом сохраняется без изменения.

### Запросы и ответственность

В кейсе 002 `requests` — объект по идентификаторам запросов. Рекомендуемые поля:

| Поле | Смысл |
|---|---|
| `type` | Что требуется: `information`, `permission`, `action`, `confirmation` |
| `from_actor` | Кто сформулировал просьбу |
| `to_actor` | Кому она адресована |
| `responsible_actor` | Кто должен дать ответ, разрешение или выполнить работу |
| `purpose` | Суть просьбы |
| `expected_response` | Что считаем достаточным ответом |
| `status` | Текущее положение запроса |
| `response` | Полученный ответ или `null` |
| `evidence_event_ids` | События, на которых основано описание |

В текущем кейсе используются статусы `planned`, `received`, `awaiting_response`, `answered`, `completed`. Это соглашение данных кейса, а не жёсткий перечень движка. Тип `permission` подходит для новых кейсов с разрешениями; в 002 отдельное согласование выбора не требуется.

`planned` означает намерение запросить что-либо. Оно не доказывает, что сообщение уже отправлено.

### Решение и варианты

Если нужен выбор, в `decision` описываются `required`, `question`, `options`, `decision_maker`, `selected_option`, `reason`. Варианты должны объяснять доступные действия и их последствия, а ответственный — указывать, кто вправе выбирать.

В 002 после уточнения причины блокировки `required: false`: нужно собрать недостающее поле и получить подтверждение исправления. Создавать искусственный выбор для каждого обращения не нужно. На старте `required: null` обозначает, что необходимость решения ещё не определена.

Формат элементов `options` пока не закреплён движком. Если новый набор кейсов требует единой структуры вариантов, её нужно согласовать как соглашение данных.

## 6. Состояние агента и ожидание

| `agent_state.status` | Когда использовать |
|---|---|
| `ready` | У агента есть доступное следующее действие |
| `acting` | В источнике зафиксировано выполнение действия в процессе |
| `waiting` | Агент ждёт конкретный ответ или результат от другого участника |
| `completed` | Работа агента по согласованной цели завершена |

Состояние относится к моменту **после** события. Поэтому шаг «Наш вопрос клиенту» содержит отправленное сообщение, а состояние после него — `waiting`.

Пример из 002 после шага 003:

```json
{
  "status": "waiting",
  "waiting_for": [
    {
      "actor_id": "recipient",
      "request_id": "r1",
      "expected": "Номер квартиры"
    }
  ],
  "next_action": "После ответа передать уточнённый адрес адресной службе."
}
```

Для `waiting` массив `waiting_for` должен содержать хотя бы один элемент с `actor_id` и `expected`. `request_id` необязателен. Для других статусов массив должен быть пустым. Можно ждать несколько участников; движок покажет все ожидания.

`next_action` объясняет следующее действие, а при ожидании — действие после получения ответа. `note` позволяет пояснить ограничение или пробел источника.

После фактической передачи задачи исполнителю агент должен ждать подтверждения исполнителя. Полученные сведения и отправленная просьба сами по себе ещё не означают выполнение работы.

В 002 отправка исправления службе отсутствует в истории. Поэтому после 004 сохранено `ready` с пояснением о необходимой передаче, а подтверждение службы приходит на 005. Промежуточный шаг `waiting` не добавлен как совершившийся факт. В новом кейсе с записанной отправкой следует явно показать: отправили службе → ждём службу → получили подтверждение.

## 7. Переписка и пояснения к источнику

`messages` содержит всю переписку, известную к выбранному шагу. Новое сообщение добавляется в конец. Уже показанные сообщения нельзя удалять, редактировать или переставлять в последующих снимках.

Обязательны `event_id`, `from_actor`, `to_actor` и текст в `body` или `body_ru`. При наличии обоих полей интерфейс показывает `body_ru`. Необязательны `timestamp` и `channel`.

Вся коммуникация идёт одной лентой, даже если различаются адресаты и каналы. JSON содержит те же сообщения, что показаны в чате; отдельно поддерживать вторую историю не нужно.

`annotations` предназначен для пояснений, которые нельзя выдавать за сообщения. Основное поле — `text`; дополнительно используются `id`, `kind`, `title`, `before_message_id`, `source_event_ids`.

Если задан `before_message_id`, пояснение появляется перед указанным сообщением. Иначе оно выводится в конце ленты. В 002 так поясняются статус отслеживания, о котором рассказал клиент, и отсутствие записанной передачи исправления службе.

Различайте подтверждённое событие, сведения со слов участника и реконструкцию автора. Реконструкции нельзя без маркировки вставлять в документальную переписку. Если нужен учебный сценарий с дополненными сообщениями, его следует подготовить отдельным файлом с явным указанием, что это моделирование.

## 8. Критерии завершения и результат

Каждый критерий содержит:

```json
{
  "id": "c2",
  "description": "Адресная служба подтвердила исправление адреса.",
  "status": "met",
  "evidence_event_ids": ["005"]
}
```

Статус бывает `pending` или `met`. Выполненному критерию нужен хотя бы один источник. Нельзя ссылаться на событие, которое ещё не наступило на выбранном шаге.

Для 002 критерии такие:

| Критерий | Подтверждение |
|---|---|
| Получен номер квартиры | Сообщение получателя 004 |
| Служба подтвердила исправление адреса | Сообщение службы 005 |
| Адресная блокировка снята | Сообщение службы 005 |

На 004 выполнен один критерий из трёх. На 005 — все три. `result` фиксирует итог, `confirmed_by` и `evidence_event_ids`; в `remaining_work` можно описать дальнейшую работу за пределами обращения.

В этом кейсе завершена координационная задача исправления адреса. Фактическая доставка не входит в её критерии: на последнем шаге посылка ещё в депо.

Автор данных отвечает за согласованность `completed`, критериев и результата. Текущий валидатор проверяет ссылки на подтверждения, но не запрещает поставить `completed` при невыполненных критериях и не оценивает, действительно ли текст источника доказывает результат.

## 9. Кейс 002 целиком в одной таблице

Исходная ситуация: у отправления DL-002 неполный адрес. Содержимое отправления в источнике не указано. Мы координируем уточнение; получатель сообщает квартиру, адресная служба вносит исправление.

| Шаг | Событие | Состояние агента после события | Критерии |
|---|---|---|---|
| Старт | Известны координатор, клиент и общая проблема | `ready`: принять сведения | 0/3 |
| 001, 09:00 | Служба → мы: в заказе нет квартиры, действует блокировка | `ready`: запросить квартиру | 0/3 |
| 002, 09:10 | Клиент → мы: видел статус отслеживания, что нужно уточнить? | `ready`: задать конкретный вопрос | 0/3 |
| 003, 09:25 | Мы → клиент: подтвердите номер квартиры | `waiting`: ждём получателя | 0/3 |
| 004, 09:50 | Клиент → мы: квартира 4B, добавьте её к адресу | `ready`: передать исправление службе; запись отправки отсутствует | 1/3 |
| 005, 10:05 | Служба → мы: адрес исправлен, блокировка снята | `completed` | 3/3 |

Все времена в таблице — UTC. Дата событий в загруженном кейсе — 2026-02-03.

## 10. Как подготовить другой кейс

1. Определите нашу роль, клиента и исполнителей. Запишите, кто отвечает за сведения, разрешение, выбор, действие и подтверждение.
2. Сформулируйте цель и проверяемые критерии завершения в пределах этой цели.
3. Составьте исходное состояние только из сведений, доступных на старте. При наличии предыдущей переписки включите её в `initial_state.messages`.
4. Выделите события в порядке источника. Для сообщений сохраните отправителя, адресата, текст, канал и время.
5. Для каждого события подготовьте полный `state_after`: обновите факты, запросы, состояние агента, переписку, критерии и результат.
6. Добавьте короткое `explanation`. Не подставляйте будущие сведения в обоснование более раннего шага.
7. Отметьте пробелы источника через `annotations` или `agent_state.note`.
8. Загрузите JSON на странице и пройдите все шаги. Проверьте, что чат, изменённые поля и состояние ожидания согласованы.

Контрольные вопросы: кто должен действовать сейчас; если агент ждёт — кого и чего; есть ли запись отправленного запроса; что изменилось после ответа; чем подтверждён каждый выполненный критерий; что осталось за пределами обращения.

## 11. Подключение и состав файлов

Виджет реализован как Web Component `<case-state-viewer>` на JavaScript без библиотек и сборки. Стили изолированы через Shadow DOM. Файлы нужно раздавать через HTTP(S).

```html
<case-state-viewer></case-state-viewer>
<script type="module">
  import './viewer.js';
  const response = await fetch('./case-002.json');
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const data = await response.json();
  const viewer = document.querySelector('case-state-viewer');
  viewer.load(data);
  viewer.addEventListener('stepchange', event => {
    console.log(event.detail.index, event.detail.state);
  });
</script>
```

| API | Поведение |
|---|---|
| `load(object)` | Копирует и проверяет данные; при успехе показывает старт |
| `goToStep(index)` | Переходит к шагу: `0` — старт, `1…N` — события |
| `stepIndex` | Возвращает выбранный индекс |
| `data` | Возвращает копию загруженного документа |
| `stepchange` | Событие перехода с `detail: { index, state }` |

`stepchange` испускается при `goToStep()`, включая переходы кнопками; `load()` отдельного такого события не испускает. Несколько экземпляров виджета независимы.

| Файл | Назначение |
|---|---|
| `viewer.js` | Валидация, сравнение состояний и компонент отображения |
| `viewer.css` | Оформление, включая критерии строками |
| `app.js` | Загрузка файла, редактор JSON, скачивание |
| `index.html` | Готовая страница с компонентом |
| `case-002.json` | Полные данные демонстрационного кейса |
| `schema.json` | JSON Schema версии 1.0 |
| `HANDOFF.md` | Это описание |

Для встраивания достаточно `viewer.js` и `viewer.css`, расположенных рядом, и объекта данных. `app.js` и `index.html` нужны для готового интерфейса загрузки. Готовый комплект файлов и команды запуска описаны в [README.md](README.md).

## 12. Проверки и границы текущей реализации

`validateCase()` проверяет обязательную основу, допустимые типы событий и состояния агента, уникальность идентификаторов событий и сообщений, участников переписки, корректность ожидания, накопление истории, наличие источников у выполненных критериев и отсутствие ссылок на будущие события. Ошибка загрузки сохраняет предыдущий кейс на экране.

`schema.json` описывает структуру; он не исполняется автоматически как полноценный JSON Schema-валидатор при загрузке. Рабочая проверка реализована в `validateCase()`. Свободные поля — например, структура `requests`, содержание `facts`, варианты решения и итог — требуют содержательной проверки автором.

Различия вычисляются как операции `add`, `replace`, `remove`. Массивы сравниваются по индексам. Для удобной подсветки сохраняйте порядок фактов и участников списка между снимками. В истории сообщений порядок менять нельзя.

Загрузка файла через интерфейс ограничена 5 МБ; текст из редактора и прямой вызов `load()` этого ограничения размера не имеют. Ограничение 1000 шагов применяется к любому способу загрузки. Большие полные снимки увеличивают объём файла и время отрисовки.

Выбранный пользователем JSON обрабатывается в браузере без отправки на сервер. Страница загружает демонстрационный JSON с сайта. Отредактированные данные остаются в памяти вкладки; для сохранения нужно нажать «Скачать JSON».

Виджет не подключён к почте, мессенджерам или системе тикетов, не отправляет сообщения, не исполняет запросы и не генерирует новые шаги. Он воспроизводит подготовленную историю. Для подключения реального агента внешняя система должна формировать события и снимки в этом формате.

Проверены воспроизведение всех снимков 002, вычисление изменений и удалений, экранирование текста, границы доступности подтверждений, обработка ошибочного ввода и загрузка второго кейса с ожиданием другого исполнителя. В опубликованном примере визуально проверены критерии строками и подтверждения на шаге 005.
