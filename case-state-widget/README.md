# Case State Widget — обращение по шагам из JSON

Интерактивный просмотр того, как агент-координатор обрабатывает обращение. На каждом шаге видны **событие → изменившиеся данные → действие или ожидание агента → переписка → критерии завершения**.

[Открыть кейс 002](https://dwelly-logistics-atlas.fly.dev/state-002.html) · [Полный разбор формата и сценария](HANDOFF.md) · [JSON Schema](schema.json)

Это самостоятельный просмотрщик подготовленной истории. Он не вызывает модель и не отправляет сообщения. Связь с proposer/evaluation harness основного репозитория пока не реализована; для неё нужен адаптер форматов.

## Каталог GitHub

Рабочая папка данных — [cases/](cases/README.md) в ветке `main`. Новые `<id>.json` появляются в переключателе без передеплоя. Сервер читает GitHub API, а кнопка «Создать PR» предлагает изменения отдельной веткой. [Подключение GitHub, доступ и PR](GITHUB.md).

## Быстрый запуск

Из корня репозитория:

```sh
LIBRARY_SOURCE=github LIBRARY_ACCESS=public CASES_DIR="$PWD/.case-library" \
STATIC_DIR="$PWD/case-state-widget" SEED_DIR="$PWD/case-state-widget" \
PORT=8080 node case-state-widget/server/server.mjs
```

Откройте [localhost:8080](http://127.0.0.1:8080). Нужен Node.js 22+; сборка, npm install и API-ключи не нужны. Если порт занят, выберите другой. [Устройство сервера, Docker и хранение](SERVER.md).

В режиме GitHub сверху показан каталог `cases/` из `main`. Загруженный файл или отредактированный JSON остаётся локальным черновиком; кнопка «Создать PR» предлагает изменение репозитория. Для приватного репозитория серверу нужен `GITHUB_READ_TOKEN`. Прежний режим серверного архива описан в [SERVER.md](SERVER.md).

Для просмотра без серверной библиотеки можно запустить `python3 -m http.server 8080 --directory case-state-widget`. Интерфейс покажет локальный режим; в нём сохранение доступно только через скачивание.

## Что на экране

- **Сверху — шаги.** Старт, отдельные события, кнопки назад/вперёд.
- **Текущее событие и агент.** Что произошло, короткое обоснование, следующее действие; при ожидании — кого и чего ждём.
- **Заявка.** Суть обращения отдельно от сообщений. Критерии идут строками: условие слева, статус и подтверждающие события справа.
- **JSON слева.** Полное состояние с подсветкой изменений относительно предыдущего шага.
- **Чат справа.** Одна лента всех сообщений; в каждом указаны отправитель и адресат, а при наличии — канал и время. Наши сообщения справа, входящие слева.
- **JSON Patch внизу.** Точные операции изменения, включая удалённые поля.

На узком экране чат и JSON располагаются друг под другом. «Мы» — участник, указанный в `our_actor_id`.

## Структура входных данных

Файл содержит **исходное состояние и полные снимки после каждого события**. JSON Patch передавать не нужно: его вычисляет движок. Порядок шагов задаётся массивом, время автоматически не сортируется.

| Поле документа | Обязательно | Назначение |
|---|---|---|
| `schema_version` | Да | Строго `case-step-viewer/1.0` |
| `title` | Да | Заголовок |
| `initial_explanation` | Нет | Пояснение к старту |
| `initial_state` | Да | Всё известное на старте |
| `steps` | Да | Массив `{ event, explanation, state_after }`, до 1000 шагов |

### Событие: `steps[].event`

| Поле | Обязательно | Назначение |
|---|---|---|
| `id` | Да | Уникальный идентификатор события |
| `type` | Да | `message_received`, `message_sent`, `action`, `state_changed` |
| `title` | Да | Что произошло |
| `label` | Нет | Короткая подпись кнопки шага |
| `timestamp` | Нет | Время строкой; показывается без преобразования часового пояса |
| `actor_id` | Нет | Участник, совершивший действие |
| `message_id` | Нет | Какое сообщение выделить в чате |

Для шага с новым сообщением используйте одинаковый ID в `event.id`, `event.message_id` и `messages[].event_id`. Направление события определяется относительно нашего агента.

`explanation` — короткое пояснение на основе доступных сведений. `state_after` — **полный** снимок после события, включая неизменившиеся поля. Например, после отправки вопроса событие — `message_sent`, а состояние агента — `waiting`.

### Состояние: `initial_state` и `steps[].state_after`

| Поле | Обязательно | Назначение |
|---|---|---|
| `actors` | Да | Объект участников по стабильным ID; значения содержат `name`, `role`, при необходимости `organization`, `responsibility` |
| `our_actor_id` | Да | Ссылка на нас в `actors` |
| `client_actor_id` | Нет | Ссылка на клиента |
| `goal` | Да | Ожидаемый результат обращения |
| `agent_state` | Да | Состояние агента, ожидания, следующее действие |
| `success_criteria` | Да | Проверяемые условия завершения |
| `messages` | Да | Накопленная переписка к этому шагу |
| `case_id`, `intake` | Нет | ID и карточка заявки: `summary`, `created_at`, `escalated_at`, `note` |
| `limits` | Нет | Запреты из раздела Limits. Один и тот же список в каждом снимке |
| `annotations` | Нет | Пояснения и пробелы источника, отдельно от сообщений |
| `facts`, `requests`, `decision`, `result` | Нет | Свободные предметные данные; видны в JSON и участвуют в diff |

Клиента и других участников, известных заранее, задайте на старте. Не переносите факты из будущих событий в ранние снимки.

### Агент: `agent_state`

- `status`: `ready` — может действовать; `acting` — выполняет действие; `waiting` — ждёт внешний ответ; `completed` — завершил работу по цели обращения.
- `waiting_for`: массив `{ actor_id, expected, request_id? }`. При `waiting` нужен хотя бы один элемент; при других статусах массив пуст.
- `next_action`: текст следующего действия или `null`. При ожидании описывает действие после ответа.
- `note`: необязательное пояснение.

После передачи задачи службе агент ждёт **подтверждения службы**. Ответ клиента с нужными сведениями сам по себе не подтверждает выполнение задачи исполнителем.

### Переписка: `messages[]`

Сообщение: `{ event_id, from_actor, to_actor, copy_to?, body?, body_ru?, channel?, timestamp? }`. ID и участники обязательны; нужен текст в `body` или `body_ru`. Если заполнены оба, интерфейс показывает `body_ru`. `to_actor` — основной адресат. `copy_to` — остальные адресаты того же сообщения; ключ пишется только когда их больше одного.

История накапливается: прошлые сообщения сохраняются без изменения и в том же порядке. В JSON и чате используется один массив. Разные адресаты и каналы остаются в общей ленте.

### Завершение: `success_criteria[]`

Критерий: `{ id, description, status, evidence_event_ids }`. Все четыре поля обязательны. Статус — `pending` или `met`; для `met` нужен хотя бы один ID уже наступившего события.

Критерии описывают результат в пределах цели обращения. Их выполнение не означает завершения всей доставки. Автор данных отвечает за согласованность `agent_state.status`, критериев и `result`: движок не вычисляет бизнес-результат самостоятельно.

### Свободные данные

Используйте одинаковую основу и свободное описание фактов вместо отдельных полей под каждый сценарий.

| Блок | Соглашение в кейсе 002 |
|---|---|
| `facts[]` | `{ id, text, source: { type, id } }` — сведения и источник |
| `requests` | Объект запросов: `type`, `from_actor`, `to_actor`, `responded_by`, `responsible_actor`, `purpose`, `expected_response`, `status`, `response`, `evidence_event_ids`. `responded_by` — кто ответил, если это не `to_actor` |
| `decision` | `required`, `question`, `options`, `decision_maker`, `selected_option`, `reason` |
| `result` | `summary`, `confirmed_by`, `evidence_event_ids`, `remaining_work` |

Тип запроса может описывать информацию, разрешение, действие или подтверждение. Адресат просьбы и ответственный исполнитель могут различаться. Если нужен выбор, запишите варианты и того, кто вправе выбирать. Если выбора нет, достаточно `decision.required: false`.

Эти поля не имеют жёсткой бизнес-схемы в текущем движке. Они отображаются как JSON; содержание и связи проверяет автор кейса.

`annotations[]` содержит `text` и, при необходимости, `id`, `kind`, `title`, `before_message_id`, `source_event_ids`. С `before_message_id` пояснение выводится перед указанным сообщением, без него — в конце ленты. Так можно явно отметить неизвестное время или пропущенное в источнике событие.

## Полный сценарий 002

[case-002.json](case-002.json) содержит пять событий из истории `Delivery & Logistics/002`:

| Шаг | Что произошло | Агент после события | Критерии |
|---|---|---|---|
| Старт | Известна проблема с неполным адресом | `ready` | 0/3 |
| 001 | Служба сообщает: нет номера квартиры | `ready` — запросить сведения | 0/3 |
| 002 | Клиент спрашивает, что нужно уточнить | `ready` — ответить клиенту | 0/3 |
| 003 | Мы запрашиваем номер квартиры | `waiting` — ждём клиента | 0/3 |
| 004 | Клиент сообщает квартиру 4B | `ready` — передать службе | 1/3 |
| 005 | Служба подтверждает исправление и снятие блокировки | `completed` | 3/3 |

Отправка исправления службе между 004 и 005 не записана в исходной истории. Она не добавлена как реальное сообщение; пробел отмечен в данных. В кейсах с записанной отправкой нужно показать соответствующее ожидание службы явно.

Клиент узнал о проблеме со страницы отслеживания — это известно из его сообщения 002. Отдельное исходящее уведомление клиенту в этот момент не выдумывается.

Размечена существующая ветка **N4 · CHANNEL_FAILURE**: форма завершилась ошибкой, и неизвестно, сохранилось ли исправление. [JSON для загрузки](examples/case-002-channel-failure.json) · [разбор шагов, выбора и критериев](examples/case-002-negative.md).

На 005 агент готов запросить проверку; на 006 ждёт службу; на 007 завершает обращение после подтверждения первой попытки. Повторная отправка исправления не производится.

## Встраивание

Расположите `viewer.js` и `viewer.css` рядом. Компонент использует Shadow DOM; готовая оболочка `app.js` для встраивания не обязательна.

```html
<case-state-viewer></case-state-viewer>
<script type="module">
  import './viewer.js';
  const response = await fetch('./case-002.json');
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const viewer = document.querySelector('case-state-viewer');
  viewer.load(await response.json());
  viewer.addEventListener('stepchange', ({ detail }) => {
    console.log(detail.index, detail.state);
  });
</script>
```

| API | Поведение |
|---|---|
| `load(object)` | Копирует и проверяет документ, показывает старт; при ошибке бросает исключение, сохраняя предыдущий кейс |
| `goToStep(index)` | Выбирает шаг: `0` — старт, `1…N` — события |
| `stepIndex` | Текущий индекс |
| `data` | Копия загруженного документа |
| `stepchange` | Событие перехода с `detail: { index, state }`; сам `load()` его не испускает |

Для проверки данных без браузера можно импортировать `validateCase()` из `viewer.js`. Экспортируются также `diffStates()`, `presentStep()` и `renderJSON()`.

## Проверки и ограничения

Тесты требуют Node.js 18+ и используют только встроенные модули:

```sh
node case-state-widget/tests/viewer.test.mjs
node case-state-widget/tests/negative-002.test.mjs
node case-state-widget/tests/server.test.mjs
```

Проверяются воспроизведение всех состояний 002, точность JSON и diff, удаление полей, экранирование текста, ожидание другого исполнителя, недопустимые ссылки на будущее, изменение прошлых сообщений и минимальный пример из README.

Рабочая проверка выполняется в `validateCase()`. `schema.json` описывает структуру, но не запускается автоматически как полноценный JSON Schema-валидатор. Семантику фактов, полномочий и доказательств проверяет автор данных; например, движок не доказывает, что текст сообщения действительно удовлетворяет критерию.

В режиме GitHub загруженные файлы и JSON из редактора остаются черновиками до PR. В прежнем режиме серверного архива они сохраняются в общей библиотеке. Лимит документа — 5 МБ, шагов — 1000. Подробности API, версий и постоянного тома: [SERVER.md](SERVER.md). В статическом локальном режиме серверного сохранения нет.

Массивы сравниваются по индексам; сохраняйте порядок элементов для читаемого diff. Удаление видно в JSON Patch и подсветке родительского объекта. Полные снимки удобны для просмотра и отладки, но увеличивают размер файла.

Подробные правила подготовки следующего кейса и разбор ответственности: [HANDOFF.md](HANDOFF.md).
