# PostgreSQL migration: dataset contract review

Reviewed 2026-10-10. Scope: proposed design, existing `CaseStore`, canonical v1 schemas, and the standalone dataset validator. This is a static compatibility review, not a PostgreSQL implementation audit or live database test. The design's reuse of `CaseStore`, canonical JSON stored as TEXT, explicit migrations, and unchanged fixture format are consistent with the dataset contract. The following are the five highest-risk acceptance checks; they are potential regression paths, not confirmed implementation defects.

1. **Preserve canonical snapshot bytes and source hashes across storage and HTTP round trips.** `CaseStore._canonical` fixes UTF-8 JSON encoding, sorted keys, compact separators, and finite numbers; `_stored_json` rejects stored text that differs from that canonical form (`tools/dwelly_service/cases.py:42`, `:154`). TEXT storage alone does not prevent a driver, HTTP adapter, or export step from reserializing Unicode, normalizing timestamp strings, or changing numeric types. Replay the same declaration/events through SQLite and PostgreSQL, including Unicode and non-UTC offsets, and compare canonical UTF-8 bytes and every revision's `snapshot_hash`/`previous_snapshot_hash`. Preserve the distinction between the canonical snapshot hash and manifest SHA-256 over exact sidecar file bytes: a pretty-print-only export change can preserve the former while invalidating the latter. Existing dataset/schema files must remain byte-identical.

2. **A duplicate request must return its original revision and create no extra analysis intent.** The current retry path returns `history[saved_revision]`, compares the canonical original body, and runs before stale revision or duplicate-event checks (`cases.py:234`, `:276`). Retry an earlier append after later revisions exist and after service restart; assert the earlier snapshot is returned, `created` is false, and head/revision/outbox counts are unchanged. Repeat with a changed body under the same key and expect `idempotency_conflict`. Verify append key scope remains per case and create scope remains separate. A PostgreSQL `ON CONFLICT` shortcut that returns the latest head would silently substitute a different dataset source triple.

3. **Observe and commit a complete, immutable revision chain atomically.** The design promises a single transaction for snapshot, head, idempotency record, and outbox (`design.md:11`). `_history` requires contiguous revisions through the head and validates immutable declaration fields and event prefixes (`cases.py:212`, `:164`). Use independent PostgreSQL connections to race two appends at one expected revision; require one winner, one `revision_conflict`, and one new intent. Inject outbox insertion failure and require full rollback. Also read during competing writes: under PostgreSQL READ COMMITTED, separate head/history queries can observe different committed states unless the transaction/lock policy explicitly prevents it. Check corruption detection with a rehashed earlier event, missing revision, or dangling head; schema validation alone is insufficient.

4. **Keep persistence and outbox lifecycle outside the frozen fixture snapshot.** The canonical schema fixes `source_mode='local_fixture'`, `runtime_binding=null`, `analysis_status='pending_not_started'`, `authorization='unverified'`, `operational_effects=0`, and `needs_analysis=true` (`contracts/v1/schemas/local-case.schema.json:50`). Hosting in PostgreSQL or Cloud SQL does not authorize changing those fields. Claim/reclaim/ack an analysis intent and prove that all snapshots and source hashes remain unchanged. Expose lifecycle metadata separately. A future production source mode or completed-analysis snapshot would require an explicit new contract rather than a storage-adapter substitution.

5. **Keep evaluator data and future evidence out of model-visible inputs and case responses.** Decision inputs allow only schema version, visibility, input ID, source, snapshot, and provenance, with `additionalProperties=false`; labels and criteria are evaluator-only (`contracts/v1/schemas/decision-input.schema.json`, `decision-label.schema.json`, `datasets/team-handoff-v1/schemas/criteria.schema.json`). Test create/read/append/error responses and the analysis-job projection against an explicit allowlist. Do not expose label rationale, acceptable dispositions, review state, criteria, future episode inputs, or worker lease tokens through joined rows or serialized internal records. A job for revision R must retain R's immutable source rather than silently fetching the latest head. Validate event times against the row's `as_of`; the current input contract has no `observed_at`, so it cannot establish when evidence became available in the real world.
